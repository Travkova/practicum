## 1. Описание задачи

Система должна автоматически анализировать входящие обращения клиентов (email-заявки) и рекомендовать диспетчеру:
- **Подразделение**, ответственное за обработку заявки
- **Приоритет** заявки (низкий / стандартный / высокий / критический)

Цель — сократить время маршрутизации, снизить количество ошибок и обеспечить своевременное выявление критических инцидентов.

---

## 2. Входные данные

| Поле | Тип | Описание | Пример |
| :--- | :--- | :--- | :--- |
| `subject` | строка (text) | Тема письма | "Не работает оплата на сайте" |
| `text` | строка (text) | Тело обращения клиента | "При попытке оплатить заказ картой, появляется ошибка 500..." |

**Ограничения входа:**
- Кодировка: UTF-8
- Язык: русский (предположение, требует подтверждения)
- Максимальная длина текста: 10 000 символов (длиннее — обрезается)
- Вложения (файлы, изображения) **не обрабатываются** в MVP

## 3. Выходные данные

| Поле | Тип | Описание | Допустимые значения |
| :--- | :--- | :--- | :--- |
| `predicted_department` | категория | Рекомендуемое подразделение | `payments`, `delivery`, `product_quality`, `tech_support`, `other` |

| `confidence_priority` | float [0, 1] | Уверенность модели в рекомендации приоритета | 0.00 – 1.00 |

**Пример ответа API:**
```json
{
  "request_id": "abc-123",
  "predicted_department": "payments",
  "predicted_priority": "high",
  "confidence_department": 0.87,

```

## 4. Тип задачи

Классификация текста (Text Classification) — задача отнесения текстового документа к одному или нескольким заранее определённым классам.
В нашем случае — многоклассовая классификация (multi-class classification) с двумя целевыми переменными:
- Подразделение (5 классов)
- Приоритет (4 класса)

---
## 5. Архитектурное решение: два классификатора или один многовыходный?

**Вариант A: Два отдельных классификатора**

Классификатор 1: текст → подразделение

Классификатор 2: текст → приоритет
*Плюсы:*
Независимое обучение и настройка каждой модели
Можно использовать разные алгоритмы (например, TF-IDF + логистическая регрессия для подразделения, трансформер для приоритета)
Проще отлаживать и интерпретировать результаты
Легче дообучать одну модель без влияния на другую
Минусы:
Два раза проходит векторизация текста (вычислительные затраты)
Не учитывает возможную корреляцию между подразделением и приоритетом

Вариант B: Один многовыходный классификатор (Multi-output)
Модель: текст → (подразделение, приоритет)
Плюсы:
Единая векторизация текста
Модель может учитывать взаимосвязь между целевыми переменными (например, заявки в payments чаще имеют приоритет high)
Проще развёртывание (одна модель вместо двух)
Минусы:
Сложнее настройка и отладка
Если одна целевая переменная "шумит" — это влияет на другую
Требует больше данных для качественного обучения

Выбранное решение: Два отдельных классификатора
Обоснование:
Разная природа задач. Подразделение определяется темой обращения (например, "оплата" → payments), а приоритет — срочностью и серьёзностью проблемы. Это разные паттерны в тексте.
Несбалансированность классов. Критические заявки встречаются редко (~5%), и отдельная модель для приоритета позволит применить техники балансировки (SMOTE, class weights) без влияния на модель подразделения.
Простота MVP. Для демонстрационного прототипа важнее скорость разработки и интерпретируемость, чем максимальная точность.
Гибкость. В будущем можно заменить одну модель на более сложную (например, трансформер для приоритета), не трогая вторую.

## 7. Правило работы с TF-IDF (и другими преобразователями)

Правильный порядок:
TfidfVectorizer().fit(train_texts) — обучаем только на train
vectorizer.transform(train_texts) — преобразуем train
vectorizer.transform(val_texts) — преобразуем validation (уже обученным векторизатором)
vectorizer.transform(test_texts) — преобразуем test (уже обученным векторизатором)
Нельзя: вызывать .fit() или .fit_transform() на validation/test — это даст завышенные метрики и модель, которая не сработает на реальных данных.

## 8. Оценка качества модели

### 8.1. Baseline-модели (точки отсчёта)

Прежде чем обучать сложные модели, зафиксируем два простых baseline, с которыми будем сравнивать улучшения.

| Baseline | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Baseline 1: Majority class** | Всегда предсказывать самый частый класс (например, `standard` для приоритета) | Показывает, насколько данные несбалансированы. Если наша модель не лучше этого baseline — она бесполезна. |
| **Baseline 2: TF-IDF + Logistic Regression** | Классический пайплайн: векторизация текста через TF-IDF, затем логистическая регрессия. Обучается **отдельно** для приоритета и для подразделения. | Реалистичный стартовый уровень. Если сложные модели (трансформеры, градиентный бустинг) не дают значимого прироста — остаёмся на этом baseline. |

**Правило:** любая следующая модель должна быть **статистически значимо лучше** baseline по ключевым метрикам (Macro F1, Recall critical), иначе усложнение неоправданно.

---

### 8.2. Метрики качества

#### Почему не Accuracy?
При несбалансированных данных (критические заявки ~5%) Accuracy вводит в заблуждение: модель, всегда предсказывающая «обычный» класс, покажет 95% точности, но пропустит все критические инциденты.

#### Используемые метрики

| Метрика | Формула / смысл | Когда использовать | Целевое значение |
| :--- | :--- | :--- | :--- |
| **Macro F1** | Среднее F1 по всем классам с **одинаковым весом** (независимо от частоты) | Когда все классы одинаково важны, даже редкие | ≥ 0.72 |
| **Weighted F1** | Среднее F1 по классам с весами, пропорциональными доле класса в выборке: $F1_{weighted} = \sum_i w_i \cdot F1_i$, где $w_i = N_i / N$ | Когда классы несут разную значимость и их количество сильно различается. Крупные классы влияют на метрику больше. | ≥ 0.72 |
| **Micro F1** | Суммирует TP, FP, FN по всем классам, сводя задачу к бинарной | Когда важен общий поток ошибок, а не поклассовый | Справочно |
| **Recall (critical)** | Доля реально критических заявок, которые модель нашла: $Recall = TP / (TP + FN)$ | **Главная метрика проекта** — цена пропуска критического инцидента максимальна | ≥ 0.80 |
| **Precision (critical)** | Доля предсказанных критических, которые действительно критические | Чтобы не перегружать диспетчера ложными тревогами | ≥ 0.70 |

**Ключевой принцип:** метрики выбираем **из цены ошибки**. Для редкого критического класса одной Accuracy недостаточно — обязательно смотрим **recall критических заявок** и **матрицу ошибок**.

---

### 8.3. Матрица ошибок (Confusion Matrix)

Для каждой модели строим матрицу ошибок отдельно по приоритету и по подразделению.

**На что смотрим в первую очередь:**
1. **Ложноотрицательные (FN) по классу `critical`** — заявки, которые модель пропустила. Это самый опасный тип ошибки.
2. **Ложноположительные (FP) по классу `critical`** — заявки, которые модель ошибочно пометила как критические. Перегружают диспетчера, но менее опасны.
3. **Путаница между `high` и `critical`** — частый сценарий; требует анализа, не систематическая ли это ошибка.

**Пример анализа:**
> «Модель путает 15% заявок класса `critical` с `high`. Это недопустимо: такие заявки не будут эскалированы вовремя. Нужно добавить признаки срочности (ключевые слова, длина текста, наличие контактов) или применить class weights.»

---

### 8.4. План оценки (по шагам)

1. **Посчитать метрики Baseline 1** (majority class) — зафиксировать нижнюю границу.
2. **Обучить Baseline 2** (TF-IDF + Logistic Regression) на train, оценить на validation.
3. **Замерить Macro F1, Weighted F1, Recall critical** на validation.
4. **Построить confusion matrix** для приоритета — найти классы, которые модель путает чаще всего.
5. **Провести анализ ошибочных критических заявок**:
   - Выбрать все FN по классу `critical`
   - Прочитать тексты этих заявок
   - Найти общие паттерны (короткий текст? специфическая лексика? опечатки?)
   - Сформулировать гипотезы по улучшению
6. **Финальная проверка** на тестовой выборке (2 000 заявок, не участвовавших в обучении/настройке).
7. **Сравнить с baseline**: если прирост Macro F1 < 5% или Recall critical не достиг 0.80 — возвращаемся к шагу 5.

## 11.План работ
EDA — разведочный анализ данных (распределение классов, длина текстов, пропуски)
Предобработка — токенизация, удаление стоп-слов, лемматизация
Векторизация — TF-IDF (fit на train, transform на val/test)
Обучение — два классификатора (логистическая регрессия / случайный лес / трансформер)
Валидация — кросс-валидация, расчёт метрик на validation
Тестирование — финальная проверка на отложенной выборке (2 000 заявок)
Деплой — упаковка в API (FastAPI / Flask)

# Нефункциональные требования проекта

> **Версия:** 1.0  
> **Статус:** черновик на согласование  
> **Ответственный:** Разработчик / архитектор + QA  
> **Дата пересмотра:** после первого прогона E2E-тестов

---

## MUST — обязательно для MVP

### NFR-M1. Скорость ответа API

**Требование:**  
Система должна возвращать рекомендацию по заявке для диспетчера при поступлении нового обращения, чтобы оператор не терял время на ожидание.

**Критерий приёмки:**  
Время ответа API ≤ 2 секунд на одну заявку при нагрузке до 10 запросов в секунду (p95 latency).

**Проверка:**  
Тестировщик запускает нагрузочный тест (например, `locust` или `ab`) на 100 запросов и фиксирует p95 latency. Заказчик наблюдает за демонстрацией прототипа в реальном времени.

**Проверяемый артефакт:**  
 Отчёт нагрузочного теста (`docs/artifacts/load-test-report.md`) + скриншот лога замера времени ответа.

---

### NFR-M2. Запуск одной командой

**Требование:**  
Система должна запускаться одной командой для разработчика или нового члена команды, чтобы сократить время онбординга и исключить ошибки ручного развёртывания.

**Критерий приёмки:**  
Команда `make run` (или `docker-compose up`) поднимает рабочее приложение на `localhost:8000` на чистой машине без предварительной ручной настройки.

**Проверка:**  
Тестировщик (или любой участник, не участвовавший в разработке) клонирует репозиторий на чистую машину/контейнер и выполняет одну команду запуска.

**Проверяемый артефакт:**  
 Скриншот терминала с успешным запуском + запись в README инструкции из одного шага.

---

### NFR-M3. Обработка некорректного ввода

**Требование:**  
Система должна возвращать понятное сообщение об ошибке для диспетчера при пустом тексте заявки или некорректном формате запроса, чтобы приложение не падало с внутренним исключением.

**Критерий приёмки:**  
При отправке пустого текста / текста только из пробелов / запроса без обязательных полей API возвращает HTTP 400 с понятным сообщением на русском языке.

**Проверка:**  
Тестировщик отправляет 5 пограничных запросов (пустая строка, только тема, спецсимволы, очень длинный текст >10 000 символов, запрос без JSON-тела) и фиксирует коды ответов.

**Проверяемый артефакт:**  
 Таблица тест-кейсов (`docs/artifacts/edge-cases-test.md`) с входными данными, ожидаемыми и фактическими ответами API.

---

##  SHOULD — желательно, но не блокирует MVP

### NFR-S1. Конфигурация отдельно от кода

**Требование:**  
Система должна позволять менять пороги уверенности модели и адреса сервисов для администратора при переносе между окружениями (dev/test/prod), чтобы не править исходный код.

**Критерий приёмки:**  
Все настраиваемые параметры (порог confidence, URL API, пути к моделям) вынесены в файл `config.yaml` или переменные окружения `.env`.

**Проверка:**  
Тестировщик меняет порог confidence в конфиге с 0.7 на 0.9 и проверяет, что модель начинает отсеивать больше заявок без пересборки кода.

**Проверяемый артефакт:**  
 Файл `config.yaml` (или `.env.example`) в репозитории + скриншот изменения поведения после правки конфига.

---

### NFR-S2. Логирование прогноза и финального решения

**Требование:**  
Система должна сохранять в лог прогноз модели и финальный выбор оператора для каждой заявки, чтобы в дальнейшем можно было дообучить модель на реальных данных.

**Критерий приёмки:**  
После обработки 10 заявок в логе (или таблице) присутствуют все поля: `request_id`, `predicted_priority`, `confidence`, `final_priority`, `timestamp`.

**Проверка:**  
Тестировщик обрабатывает 10 тестовых заявок (5 подтверждает, 5 изменяет) и сверяет содержимое лога с ожидаемым форматом.

**Проверяемый артефакт:**  
 Выгрузка лога (`docs/artifacts/log-sample.csv`) с 10 записями + схема полей.

---

##  COULD — по возможности, не входит в MVP

### NFR-C1. Поиск похожих исторических заявок

**Требование:**  
Система должна показывать диспетчеру 3 похожие исторические заявки при открытии обращения, чтобы ускорить принятие решения на основе прецедентов.

**Критерий приёмки:**  
При открытии заявки в интерфейсе отображается блок «Похожие обращения» с релевантными результатами (cosine similarity > 0.7).

**Проверка:**  
Заказчик вручную оценивает релевантность 10 выданных рекомендаций по 5-балльной шкале; средняя оценка ≥ 4.

**Проверяемый артефакт:**  
 Прототип блока в UI + таблица оценки релевантности от заказчика (`docs/artifacts/similar-tickets-evaluation.md`).

>  **Важно:** это требование **не включается в MVP**, пока не закрыты базовые сценарии (NFR-M1, NFR-M2, NFR-M3).
